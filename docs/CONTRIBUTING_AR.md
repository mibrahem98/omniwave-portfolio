# كيف تساهم في OmniWave

شكرًا لرغبتك في تطوير OmniWave. المشروع مركز وسائط محلي للهواتف، لذلك تُقيَّم أي مساهمة وفق نتيجتها للمستخدم، وخصوصية ملفاته، وإتاحتها، وقدرتها على العمل على iOS وAndroid بصورة مسؤولة. توضح هذه الصفحة المسار العملي للمساهمة باللغة العربية، وتكمل [دليل المساهمة الإنجليزي](../CONTRIBUTING.md) و[قواعد السلوك](../CODE_OF_CONDUCT.md).

> **المبدأ الحاكم:** تبقى الموسيقى والفيديوهات ومسارات الملفات وURI وسجل الاستماع والتفضيلات على جهاز المستخدم افتراضيًا. لا تضف حسابات أو مزامنة سحابية أو إعلانات أو تحليلات خارجية إلا بتغيير نطاق موثق وموافقة صريحة.

## 1. تجهيز بيئة العمل

استعمل إصدار Node وpnpm المحددين في المستودع، ثم ثبت الحزم وشغّل خادم التطوير.

```bash
pnpm install
pnpm dev
```

يعرض خادم Expo المعاينة ومسارات الواجهة، بينما يحتاج السلوك الأصلي إلى جهاز حقيقي. استخدم الأوامر التالية عند الحاجة إلى محاكي أو جهاز متصل:

| الهدف | الأمر |
|---|---|
| فحص الأنواع | `pnpm check` |
| قواعد الجودة | `pnpm lint` |
| اختبارات Vitest | `pnpm test` |
| Android | `pnpm android` |
| iOS | `pnpm ios` |

## 2. اختيار نطاق صغير وواضح

ابدأ بنتيجة واحدة يمكن للمستخدم ملاحظتها، مثل تحسين صف مسار، توسيع حالة استيراد، إصلاح ترجمة RTL، أو إضافة اختبار لتفضيل محفوظ. لا تجمع إعادة تصميم واسعة وإعادة هيكلة للحالة وإضافة حزمة جديدة في طلب واحد؛ فهذا يصعّب المراجعة ويخفي أثر كل تغيير.

| قبل البدء | ما يجب تأكيده |
|---|---|
| المشكلة | ما السلوك الحالي؟ وما النتيجة المطلوبة القابلة للتحقق؟ |
| البيانات | هل تمس `Track` أو`Playlist` أو`PlayerSnapshot` أو`AudioPreferences` أو نماذج الفيديو؟ |
| الخصوصية | هل تظل الملفات والـURI والبيانات الوصفية داخل الجهاز؟ |
| الإتاحة | هل يوجد وصف وصول وبديل مرئي للإيماءة أو اللون وحالة تقليل حركة؟ |
| اللغات | هل تحتاج مفاتيح نصية في العربية والإنجليزية والفرنسية والإسبانية مع فحص RTL؟ |
| المنصات | هل يمس التغيير الخلفية أو شاشة القفل أو Bluetooth أو المشاركة أو PiP أو الصلاحيات؟ |

## 3. قواعد الشفرة والبيانات

اقرأ [الضوابط الهندسية](../ENGINEERING_GUARDRAILS.md) و[فهرس الملفات](FILE_CATALOG.md) قبل التعديل. مرر التغييرات عبر إجراءات واضحة في طبقة الحالة ولا تجعل المكونات واجهة لعمليات التخزين أو الصوت الحساسة مباشرة. تحقق من كل URI واسم ملف وبيان وصفي قبل الحفظ أو التشغيل، وحد أطوال المصفوفات والنصوص عند الاستعادة المحلية.

استخدم `ScreenContainer` للشاشات، ومفاتيح `localization.ts` لكل نص واجهة جديد، وأضف تعليقات وصول للأزرار وعناصر التحكم. لا تعتمد على اللون أو السحب أو الاهتزاز وحده لإيصال معنى أو نتيجة. إذا أضفت حركة، وفر حالة ثابتة متماسكة عندما يختار المستخدم تقليل الحركة.

## 4. حماية الخصوصية والمواد الحساسة

لا ترفع أو تلتزم أو تضف إلى لقطة شاشة أو بلاغ أو طلب دمج أي ملف صوت أو فيديو، URI محلي، مسار، رمز جلسة، بيانات اعتماد، معرف جهاز، أو سجل استماع شخصي. استخدم بيانات اختبار مرخصة أو وصفية لا تحمل بيانات شخص حقيقي. عند إضافة مشاركة أو تصدير، راجع الناتج يدويًا للتأكد من أنه لا يكشف اسم الملف الخام أو مساره أو URI.

> لا تسجل طبقات التطبيق عنوان المسار أو URI أو اسم الملف في سجلات الإنتاج. تعامل مع كل مدخل محلي بوصفه غير موثوق، بما يشمل الإدخالات المستعادة من التخزين.

## 5. الاختبار قبل طلب المراجعة

نفذ بوابات الجودة كاملة قبل فتح طلب دمج:

```bash
git diff --check
pnpm check
pnpm lint
pnpm test
```

أضف أو حدّث اختبار Vitest عند تغيير تدفق، أو عقد بيانات، أو قاعدة حفظ، أو حد تصدير، أو عنصر تحكم متاح. اختبر واجهة عربية بعناوين طويلة، مع حجم نص كبير، وتباين عالٍ، وتقليل الحركة عندما يمس التغيير هذه الحالات.

| نوع التغيير | الدليل المطلوب |
|---|---|
| واجهة أو ترجمة | وصف السلوك، اختبار عقد أو لقطة عند الحاجة، وفحص RTL والإتاحة. |
| تخزين أو استيراد | اختبار إدخال تالف وإلغاء وتكرار واستعادة بيانات غير صالحة. |
| مشاركة أو تصدير | معاينة ناتج خالٍ من المسارات وURI والبيانات الشخصية. |
| صوت أو فيديو أصلي | نتيجة بناء واختبار iOS وAndroid حقيقيين، أو تصريح واضح بأن الاختبار ما زال مطلوبًا. |

معاينة الويب لا تثبت تشغيل الخلفية أو شاشة القفل أو مخرج الصوت أو Bluetooth أو منتقي النظام أو المشاركة أو PiP أو التدوير. لا تصف هذه الميزات بأنها «متحقق منها» إلا بعد اختبارها على الأجهزة المستهدفة. راجع [مصفوفة الاختبارات الأصلية](NATIVE_TEST_MATRIX_IOS_ANDROID.md) عند تنفيذ سلوك أصلي.

## 6. فتح طلب دمج واضح

استخدم فرعًا ذا اسم وصفي، واجعل طلب الدمج مركزًا على نتيجة واحدة. اشرح ماذا تغير ولماذا، ثم أضف أدلة الاختبار وملخص أثر الخصوصية واللغات والإتاحة. اذكر صراحةً أي اختبار أصلي لم ينفذ بعد بدل إخفاء هذا القيد.

| قسم طلب الدمج | مثال موجز |
|---|---|
| النتيجة | «إظهار حالة قابلة لإعادة المحاولة عند إلغاء استيراد الفيديو». |
| الدافع | «منع غموض الواجهة بعد إلغاء منتقي النظام». |
| الخصوصية | «لا تخزن العملية إلا بيانات محلية متحققة؛ لا يوجد نقل خارجي». |
| الإتاحة وRTL | «زر إعادة المحاولة له تسمية وصول ونص مترجم ولا يعتمد على اللون». |
| الاختبارات | «نجح `pnpm check` و`pnpm lint` و`pnpm test`؛ اختبار Android الأصلي ما زال مطلوبًا». |

## 7. الإبلاغ عن مشكلة أو اقتراح

استخدم نماذج Issues في المستودع للبلاغات واقتراحات الميزات. اشرح خطوات إعادة الإنتاج والسلوك المتوقع والفعلي وبيئة الاختبار، لكن احذف البيانات الحساسة. ينبغي أن يوضح اقتراح الميزة أثره في البيانات المحلية وRTL وتقليل الحركة والإتاحة قبل تنفيذه.

كن محترمًا ومحددًا وقابلًا للتنفيذ في المراجعات والنقاشات. تطبق [قواعد السلوك](../CODE_OF_CONDUCT.md) على Issues وطلبات الدمج والمراجعات وكل التفاعلات المرتبطة بالمشروع. بلّغ عن سلوك غير مناسب من خلال أدوات الإبلاغ في GitHub أو تواصل خاص مع مالك المستودع مع الحد الأدنى اللازم من المعلومات.

## قائمة مراجعة المساهم

- [ ] نطاق التغيير صغير ومربوط بنتيجة واضحة للمستخدم.
- [ ] لا تحتوي الشفرة أو الوثائق أو الصور على ملفات أو مسارات أو URI أو رموز أو تاريخ شخصي.
- [ ] تحققت من كل بيانات محلية جديدة قبل حفظها أو تشغيلها.
- [ ] أضفت النصوص المترجمة وفحصت RTL والإتاحة وتقليل الحركة عند الحاجة.
- [ ] نجحت بوابات الجودة وأرفقت أدلتها في طلب الدمج.
- [ ] وثقت اختبار الجهاز الحقيقي أو القيد المتبقي عندما يكون التغيير أصليًا.
